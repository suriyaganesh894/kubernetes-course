L1

Why Kubernetes?

About 10 minutes. No installs yet.

You can explain what Kubernetes does that Docker alone doesn’t.

Explain like I’m 5

With Docker, you learned to pack toys into boxes. That’s great when you have one toy box on one shelf.

Now imagine a giant toy shop with a thousand boxes and fifty shelves. Someone has to decide which shelf each box goes on, notice when a shelf breaks and move its boxes, put out more boxes when lots of kids arrive, and take some away when the shop is quiet.

Kubernetes is that shop manager. You don’t tell it how to do things. You tell it what you want, like “always keep five teddy-bear boxes out”, and it makes it true, all day and all night.

The engineer’s view

Kubernetes (often written K8s: K, eight letters, s) is an open-source container orchestrator, originally from Google and now run by the Cloud Native Computing Foundation. Its name is Greek for “helmsman”.

What it gives you:

  • Scheduling: places containers on machines with enough free CPU and memory.
  • Self-healing: restarts crashed containers and replaces ones on failed machines.
  • Scaling: more or fewer copies, by hand or automatically.
  • Service discovery and load balancing: a stable name and IP in front of changing containers.
  • Rolling updates and rollbacks: new versions with zero downtime.
  • Config and secrets, storage, and a huge ecosystem of extensions.

The core idea is declarative desired state. You write down what you want (in YAML), send it to the cluster, and controllers keep comparing “what is” with “what should be” and fixing the difference. This loop is called reconciliation.

Kubernetes isn’t always the answer. For one small app on one server, Docker Compose is simpler. Kubernetes pays off when you have many services, many machines, or need high availability.

Hands-on: imperative vs declarative

No computer needed. Compare these two ways to get pizza for a party of ten.

  1. Imperative: “Call the shop. Order two pizzas. When they arrive, count. If one is missing, call again.” Write down what happens if you fall asleep.
  2. Declarative: “There should always be at least two pizzas on the table.” Who needs to be awake now?
  3. Write your own declarative sentence for a website: how many copies, which version, how much memory each.
Show an example answer

“Run 3 copies of shop-web version 2.1, each with 256 MB of memory, reachable at the name shop-web.” That sentence is almost exactly a Kubernetes Deployment plus a Service, as you’ll write in lessons 6 and 7.

Remember

  • Kubernetes orchestrates containers across many machines.
  • You declare what you want; controllers keep reality matching it.
  • Self-healing, scaling, load balancing and rolling updates come built in.

Cluster architecture

About 15 minutes.

You can name every piece of a cluster and say what it does.

Explain like I’m 5

Think of a school. The head office is the control plane. Inside it:

The receptionist (API server) is the only person you talk to. The big notebook (etcd) remembers everything. The timetable maker (scheduler) decides which classroom each class goes to. The hall monitors (controllers) walk around checking everything matches the notebook.

The classrooms are the worker nodes. Each has a teacher (kubelet) who makes sure the right kids are in the room, and a door person (kube-proxy) who directs visitors to the right desk.

The engineer’s view
ComponentRuns onJob
kube-apiserverControl planeFront door. Validates and stores every request. kubectl, nodes and controllers all talk to it.
etcdControl planeConsistent key-value store holding the whole cluster state. Back it up!
kube-schedulerControl planePicks a node for each new Pod based on resources and rules.
kube-controller-managerControl planeRuns controllers (Deployment, ReplicaSet, Node, Job…) that reconcile state.
cloud-controller-managerControl plane (cloud)Talks to the cloud for load balancers, disks, node lifecycle.
kubeletEvery nodeAgent that starts and watches the Pods assigned to its node.
kube-proxyEvery nodePrograms networking rules so Services route to Pods.
Container runtimeEvery nodecontainerd or CRI-O actually runs containers.

What happens when you create a Deployment: kubectl sends YAML to the API server → stored in etcd → the Deployment controller creates a ReplicaSet → the ReplicaSet controller creates Pods → the scheduler assigns each Pod to a node → that node’s kubelet tells containerd to pull the image and start the containers → status flows back to the API server.

Kubernetes removed direct Docker Engine support (the “dockershim”) in version 1.24. Images built with Docker still work perfectly, because they follow the OCI standard that containerd understands.

Hands-on: draw the journey
  1. On paper, draw the eight components above as boxes.
  2. Draw numbered arrows for “I ran kubectl create deployment web --image=nginx”. Use the paragraph above to check.
  3. After lesson 3, verify with real components: kubectl get pods -n kube-system lists the control plane parts running as Pods.
What if the control plane goes down?

Running Pods keep running, because kubelets keep them alive. But nothing new can be scheduled, scaled or healed until the control plane is back. That’s why production clusters run three or more control-plane nodes.

Remember

  • Control plane: API server, etcd, scheduler, controller manager.
  • Each node: kubelet, kube-proxy, container runtime.
  • Everything goes through the API server.

Pods

About 25 minutes.

You can create, inspect, enter and delete Pods, and explain why Pods (not containers) are Kubernetes’ smallest unit.

Explain like I’m 5

Peas grow inside a pea pod. The peas in one pod are always together: they share the same pod, travel together, and get picked together.

In Kubernetes, containers live inside a Pod. Usually there’s just one pea (one container). Sometimes there’s a helper pea too, like a little friend who collects the main pea’s diary pages and posts them. Peas in the same pod share one address and can share a lunchbox (storage).

Your first Pod in YAML
apiVersion: v1          # which API group/version
kind: Pod               # what type of object
metadata:
  name: hello
  labels:
    app: hello
spec:                   # what you want
  containers:
    - name: web
      image: nginx:1.27-alpine
      ports:
        - containerPort: 80
  • Every object has apiVersion, kind, metadata and usually spec. The cluster adds a status section describing reality.
  • Pods are disposable (“cattle, not pets”). If a Pod dies, nothing recreates it unless a controller (like a Deployment) owns it. In real life you rarely create bare Pods.
  • Pod phases: Pending → Running → Succeeded or Failed (plus Unknown). Container states: Waiting, Running, Terminated.
  • Multi-container patterns: sidecar (helper alongside the app), init container (runs to completion before the app starts), ambassador/adapter.
apiVersion: v1
kind: Pod
metadata:
  name: waiter
spec:
  initContainers:
    - name: wait-for-db
      image: busybox:1.36
      command: ["sh", "-c", "until nslookup db; do echo waiting; sleep 2; done"]
  containers:
    - name: app
      image: nginx:1.27-alpine
Hands-on: grow some peas
  1. Create the Pod from YAML and watch it start: 
    $ kubectl apply -f pod.yaml
pod/hello created
$ kubectl get pods -o wide
NAME    READY   STATUS    IP            NODE
hello   1/1     Running   10.244.1.7    fleet-worker
  2. Read its full story. The Events at the bottom are gold for debugging. 
    $ kubectl describe pod hello
  3. Look inside, read logs, and reach it from your laptop: 
    $ kubectl exec -it hello -- sh
/ # wget -qO- localhost | head -n 4
/ # exit
$ kubectl logs hello
$ kubectl port-forward pod/hello 8080:80
    Open http://localhost:8080, then Ctrl+C.
  4. Delete it and notice nobody brings it back: 
    $ kubectl delete pod hello
$ kubectl get pods
No resources found in default namespace.
  5. Generate YAML instead of typing it (a pro trick you’ll use forever): 
    $ kubectl run demo --image=nginx:1.27-alpine --dry-run=client -o yaml > demo.yaml
Write a Pod with two containers: nginx, and a busybox container running sh -c "while true; do wget -qO- localhost; sleep 5; done". Check the busybox logs. Why does localhost reach nginx? Use kubectl logs POD -c CONTAINER.

Remember

  • A Pod wraps one or more containers sharing an IP and volumes.
  • Bare Pods aren’t recreated when deleted. Use controllers.
  • apply, get, describe, logs, exec, port-forward, delete.

YAML, labels & namespaces

About 20 minutes.

You can read any manifest, find things with labels, and keep teams apart with namespaces.

Explain like I’m 5

Labels are coloured stickers. You can put a “red” sticker and a “big” sticker on a ball. Later you can say “bring me everything with a red sticker” and get all the red things, whatever they are. That question is a selector.

Namespaces are separate rooms in a house. Your toys go in your room, your sister’s in hers. You can both have a toy called “teddy” without mixing them up.

YAML survival kit
# key: value
name: web
replicas: 3            # number
enabled: true          # boolean
version: "1.0"         # quote strings that look like numbers

# map (dictionary): indent with SPACES, never tabs
metadata:
  name: web
  labels:
    app: shop
    tier: frontend

# list: dash + space
ports:
  - containerPort: 80
  - containerPort: 443

# inline forms work too
selector: { app: shop }
args: ["--port", "80"]

---   # three dashes separate multiple objects in one file

Labels, selectors, annotations

  • Labels identify and group objects. Services, Deployments and NetworkPolicies find Pods by label. Common keys: app.kubernetes.io/name, app.kubernetes.io/version, tier, env.
  • Selectors: equality (app=shop, env!=prod) and set-based (env in (dev,qa)).
  • Annotations hold non-identifying notes for tools (build info, ingress settings). They can’t be selected on.

Namespaces

Default ones: default, kube-system (cluster parts), kube-public, kube-node-lease. Names must be unique only inside a namespace. Some objects are cluster-wide and have no namespace: Nodes, PersistentVolumes, StorageClasses, ClusterRoles, Namespaces themselves.

Namespaces separate names and permissions, not network traffic. Pods in different namespaces can talk to each other by default. Use NetworkPolicies (lesson 17) to block that.

Hands-on: stickers and rooms
  1. Make two rooms and put Pods in them: 
    $ kubectl create namespace dev
$ kubectl create namespace prod
$ kubectl run web --image=nginx:1.27-alpine -n dev -l app=shop,tier=frontend
$ kubectl run api --image=nginx:1.27-alpine -n dev -l app=shop,tier=backend
$ kubectl run cache --image=redis:7-alpine -n dev -l app=redis
$ kubectl run web --image=nginx:1.27-alpine -n prod -l app=shop
    Two Pods called web, no conflict.
  2. Ask by sticker: 
    $ kubectl get pods -n dev -l app=shop
$ kubectl get pods -n dev -l 'tier in (frontend)'
$ kubectl get pods -A -l app=shop --show-labels
  3. Add and change stickers live: 
    $ kubectl label pod cache -n dev env=test
$ kubectl label pod cache -n dev env=staging --overwrite
$ kubectl annotate pod cache -n dev owner="team-blue"
  4. Make dev your default room so you can stop typing -n dev: 
    $ kubectl config set-context --current --namespace=dev
  5. Clean up both rooms at once (deleting a namespace deletes everything inside): 
    $ kubectl config set-context --current --namespace=default
$ kubectl delete namespace dev prod

Remember

  • YAML: spaces not tabs, dashes for lists, --- between objects.
  • Labels + selectors are how Kubernetes objects find each other.
  • Namespaces separate names and permissions, not network traffic.

ReplicaSets & Deployments

About 25 minutes. The object you’ll write most often.

You can run an app as several self-healing copies and scale it with one command.

Explain like I’m 5

You tell the babysitter: “There must always be three kids on the swings.” If one kid goes home, the babysitter brings another. If four show up, one is asked to go play somewhere else. That babysitter is a ReplicaSet.

A Deployment is the babysitter’s boss. When it’s time for new swings, the boss carefully moves kids from the old swings to the new ones, a few at a time, so the playground is never empty.

A Deployment manifest
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  labels: { app: web }
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web            # must match the template labels below
  template:               # a Pod template: the cookie cutter
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.27-alpine
          ports:
            - containerPort: 80
  • The selector must match template.metadata.labels, or the API server rejects it.
  • Pod names get a ReplicaSet hash and a random suffix: web-7d9f8c6b5-abcde.
  • You almost never create ReplicaSets yourself. Deployments create one per version, which enables rollbacks (lesson 8).
  • Imperative (kubectl scale) and declarative (kubectl apply) can fight: if you scale by hand and then re-apply a file saying 3, you’re back to 3. Prefer editing the file.
Hands-on: the unbeatable babysitter
  1. Apply and look at the whole family: 
    $ kubectl apply -f deploy.yaml
$ kubectl get deploy,rs,pods -l app=web
NAME                  READY   UP-TO-DATE   AVAILABLE
deployment.apps/web   3/3     3            3
NAME                            DESIRED   CURRENT   READY
replicaset.apps/web-7d9f8c6b5   3         3         3
  2. In a second terminal, watch: kubectl get pods -l app=web -w. In the first, delete a Pod: 
    $ kubectl delete pod $(kubectl get pods -l app=web -o name | head -n 1)
    Watch a replacement appear within a second or two.
  3. Scale up and down: 
    $ kubectl scale deployment web --replicas=6
$ kubectl get pods -l app=web -o wide     # spread across both workers
$ kubectl scale deployment web --replicas=2
  4. Be sneaky: remove the label from a Pod so it no longer matches. 
    $ kubectl label pod POD_NAME app-     # the trailing dash removes the label
$ kubectl get pods --show-labels
    The ReplicaSet makes a new Pod to get back to 2, and the orphan keeps running on its own. (This is how you quarantine a misbehaving Pod for debugging.)
  5. Keep the web Deployment for the next lesson. Delete the orphan Pod.

Remember

  • Deployment → ReplicaSet → Pods.
  • ReplicaSets keep the count right by matching labels.
  • Change replicas in YAML and kubectl apply; that’s the declarative way.

Services

About 30 minutes.

Your Pods get one stable name and address, inside and outside the cluster.

Explain like I’m 5

Pods come and go, and each new one gets a new phone number. Calling them directly is hopeless.

A Service is like a pizza shop’s main phone number. You always call the same number. Behind it, whichever cook is free picks up. Cooks can change shifts all day, and you never notice.

Service types
TypeReachable fromUse
ClusterIP (default)Inside the cluster onlyTalking between your own services
NodePortEvery node’s IP on a port 30000–32767Quick external access, labs, bare metal
LoadBalancerA cloud load balancer’s public IPExposing a service on AWS/GCP/Azure
ExternalNameDNS alias to an outside namePointing at an external database
Headless (clusterIP: None)DNS returns Pod IPs directlyStatefulSets, client-side balancing
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: ClusterIP
  selector:
    app: web            # which Pods
  ports:
    - port: 80          # the Service's port
      targetPort: 80    # the container's port

DNS names: inside the same namespace just use web. From another namespace: web.NAMESPACE, or fully web.NAMESPACE.svc.cluster.local. CoreDNS provides this.

If a Service doesn’t work, run kubectl get endpointslices -l kubernetes.io/service-name=web. Empty? Your selector doesn’t match any ready Pod’s labels. That’s the cause nine times out of ten.

  1. Make the web Deployment show which Pod answers, then expose it: 
    $ kubectl scale deployment web --replicas=3

$ kubectl apply -f svc.yaml
$ kubectl get svc web
NAME   TYPE        CLUSTER-IP     PORT(S)
web    ClusterIP   10.96.12.34    80/TCP
  2. Call it from a throwaway client Pod, several times: 
    $ kubectl run client --rm -it --image=busybox:1.36 --restart=Never -- sh
/ # for i in 1 2 3 4 5 6; do wget -qO- web; done
hi from web-7d9f8c6b5-abcde
hi from web-7d9f8c6b5-q8w2r
hi from web-7d9f8c6b5-xk2p9
/ # nslookup web
/ # exit
  3. Reach it from your laptop without changing the Service: 
    $ kubectl port-forward svc/web 8080:80
  4. Try a NodePort: 
    $ kubectl expose deployment web --name=web-np --type=NodePort --port=80
$ kubectl get svc web-np

    On kind, nodes are Docker containers, so test from inside: docker exec fleet-worker curl -s localhost:31234.
  5. Break it on purpose: kubectl patch svc web -p '{"spec":{"selector":{"app":"oops"}}}', check the EndpointSlice is empty, then fix it back to app: web.

Remember

  • Services give Pods a stable name, IP and load balancing.
  • ClusterIP inside, NodePort/LoadBalancer outside.
  • Empty endpoints = selector doesn’t match ready Pods.

Rolling updates & rollbacks

About 20 minutes.

Ship a new version with zero downtime, and undo it in seconds if it’s bad.

Explain like I’m 5

A relay team is running round a track and you want fresh runners. You don’t stop the race. A new runner joins, an old one steps off, then the next, then the next. The race never stops.

And if a new runner trips? You call the old runners back. That’s a rollback.

The engineer’s view
spec:
  replicas: 4
  revisionHistoryLimit: 5       # keep 5 old ReplicaSets for rollback
  minReadySeconds: 5            # a Pod must stay Ready 5s to count
  strategy:
    type: RollingUpdate         # or Recreate (kill all, then start all)
    rollingUpdate:
      maxSurge: 1               # at most 1 extra Pod during the update
      maxUnavailable: 0         # never go below 4 ready Pods
  • Any change to the Pod template (image, env, labels…) triggers a rollout and a new ReplicaSet. Changing replicas doesn’t.
  • Rollouts depend on readiness probes (lesson 12). Without one, Kubernetes assumes a Pod is ready as soon as it starts, even if your app takes 30 seconds to boot.
  • Blue-green (two full Deployments, switch the Service selector) and canary (send a small share of traffic to v2) are patterns built on top, often with tools like Argo Rollouts or a service mesh.

Record why you changed something with an annotation: kubectl annotate deploy web kubernetes.io/change-cause="upgrade to 1.27.1". It shows up in rollout history.

Hands-on: swap the runners
  1. In one terminal, watch Pods: kubectl get pods -l app=web -w. In another, update the image: 
    $ kubectl set image deployment/web web=nginx:1.27.1-alpine
$ kubectl rollout status deployment/web
Waiting for deployment "web" rollout to finish: 2 of 3 updated replicas are available...
deployment "web" successfully rolled out
  2. See two ReplicaSets and the history: 
    $ kubectl get rs -l app=web
$ kubectl rollout history deployment/web
  3. Ship a broken version (this tag doesn’t exist): 
    $ kubectl set image deployment/web web=nginx:does-not-exist
$ kubectl get pods -l app=web
web-5c…   0/1   ImagePullBackOff
web-7d…   1/1   Running        ← old Pods still serving!
    The rollout stalls but your app stays up, because new Pods never become Ready.
  4. Roll back: 
    $ kubectl rollout undo deployment/web
$ kubectl rollout undo deployment/web --to-revision=1   # or pick a revision
  5. Other handy rollout tools: kubectl rollout pause|resume deployment/web to batch changes, and kubectl rollout restart deployment/web to recycle all Pods (for example, to pick up a changed ConfigMap).

Remember

  • Changing the Pod template starts a rolling update; old ReplicaSets enable rollback.
  • maxSurge and maxUnavailable control the pace.
  • rollout status, history, undo, restart.

ConfigMaps & Secrets

About 25 minutes.

Keep settings and passwords outside your image and feed them to Pods as variables or files.

Explain like I’m 5

A ConfigMap is the notice board in the classroom: “Lunch is at 12. Today’s colour is blue.” Anyone can read it, and you can change it without changing the kids.

A Secret is a sealed envelope for things like the code to the treasure chest. Only kids who are allowed get to open it.

The engineer’s view
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: "info"
  FEATURE_X: "true"
  config.yaml: |               # a whole file as one key
    greeting: Hello from a ConfigMap
    colour: blue
---
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
type: Opaque
stringData:                    # plain text in; stored base64-encoded
  DB_PASSWORD: "s3cr3t-pa55"
apiVersion: v1
kind: Pod
metadata:
  name: configured
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "echo $LOG_LEVEL $DB_PASSWORD; cat /etc/app/config.yaml; sleep 3600"]
      envFrom:
        - configMapRef: { name: app-config }   # every key becomes an env var
      env:
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef: { name: app-secret, key: DB_PASSWORD }
      volumeMounts:
        - name: cfg
          mountPath: /etc/app
          readOnly: true
  volumes:
    - name: cfg
      configMap:
        name: app-config
        items: [{ key: config.yaml, path: config.yaml }]

Secrets are only base64-encoded, not encrypted. Anyone who can read them in the API can decode them in one command. Protect them with RBAC (lesson 17), turn on encryption at rest for etcd, never commit plain Secret YAML to git, and consider tools like External Secrets Operator, Sealed Secrets, or a cloud secret manager.

Mark a ConfigMap or Secret immutable: true when it should never change. It’s safer and lighter on the API server.

Storage: PV, PVC & StorageClass

About 25 minutes.

Probes, requests & limits

About 30 minutes. Skipping this lesson is the most common cause of production outages.

Kubernetes knows when your app is alive and ready, and how much CPU and memory it needs.

Explain like I’m 5

Three questions a teacher asks every child:

“Are you awake?” If not, gently wake them up again (that’s a liveness probe: restart if stuck). “Are you ready to answer questions?” If not, don’t ask them yet; ask someone else (readiness probe: no traffic until ready). “Have you finished getting dressed?” Slow dressers get extra time before the other questions start (startup probe).

And at lunch: each child is promised at least one sandwich (request) and can’t take more than three (limit).

The engineer’s view
containers:
  - name: api
    image: ghcr.io/you/api:1.4.0
    ports: [{ containerPort: 8080 }]
    resources:
      requests:
        cpu: "250m"          # a quarter of a CPU core
        memory: "128Mi"
      limits:
        memory: "256Mi"      # over this → OOMKilled
        # cpu limit optional: over it the app is throttled, not killed
    startupProbe:
      httpGet: { path: /healthz, port: 8080 }
      failureThreshold: 30
      periodSeconds: 2       # up to 60s to start
    readinessProbe:
      httpGet: { path: /ready, port: 8080 }
      periodSeconds: 5
    livenessProbe:
      httpGet: { path: /healthz, port: 8080 }
      periodSeconds: 10
      failureThreshold: 3
  • Probe types: httpGet, tcpSocket, exec (a command), grpc.
  • A readiness endpoint can check dependencies (database reachable). A liveness endpoint should not, or a database outage will restart every Pod in a loop.
  • QoS classes: Guaranteed (requests = limits for all), Burstable (some requests), BestEffort (nothing set: evicted first when a node runs short).
  • Namespace-level guardrails: LimitRange sets defaults per container; ResourceQuota caps a namespace’s total.

Units: CPU 1 = one core = 1000m. Memory Mi/Gi are powers of two; M/G are powers of ten.

Hands-on: wake-up calls
  1. A Pod whose liveness file disappears after 30 seconds: 
    apiVersion: v1
kind: Pod
metadata:
  name: sleepy
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "touch /tmp/alive; sleep 30; rm /tmp/alive; sleep 600"]
      livenessProbe:
        exec: { command: ["cat", "/tmp/alive"] }
        initialDelaySeconds: 5
        periodSeconds: 5
    $ kubectl apply -f liveness.yaml
$ kubectl get pod sleepy -w
sleepy   1/1   Running   0     40s
sleepy   1/1   Running   1 (2s ago)   52s     ← restarted
$ kubectl describe pod sleepy | grep -A3 Liveness
  2. Readiness without restarts: make one web Pod unready and watch the Service skip it. 
    $ kubectl patch deployment web --type=json -p='[{"op":"add","path":"/spec/template/spec/containers/0/readinessProbe","value":{"exec":{"command":["cat","/tmp/ready"]},"periodSeconds":3}}]'
$ kubectl get pods -l app=web       # 0/1 READY: no /tmp/ready yet
$ kubectl exec POD_NAME -- touch /tmp/ready
$ kubectl get endpointslices -l kubernetes.io/service-name=web
  3. Get OOMKilled on purpose: 
    apiVersion: v1
kind: Pod
metadata:
  name: hog
spec:
  restartPolicy: Never
  containers:
    - name: hog
      image: polinux/stress
      command: ["stress", "--vm", "1", "--vm-bytes", "100M"]
      resources:
        limits: { memory: "50Mi" }
    $ kubectl apply -f hog.yaml

hog   0/1   OOMKilled
  4. See what nodes have promised: kubectl describe node fleet-worker | grep -A8 "Allocated resources". Clean up: kubectl delete pod sleepy hog.

Remember

  • Startup = slow boot, readiness = traffic on/off, liveness = restart if stuck.
  • Always set memory requests and limits; set CPU requests.
  • Don’t check dependencies in liveness probes.

You’ll pick the right workload type for databases, per-node agents, one-off tasks and schedules.

Explain like I’m 5

Deployment: identical robots. Any robot can replace any other.

The engineer’s view
apiVersion: v1

metadata:

kind: StatefulSet

  name: db

      backoffLimit: 2
      template:
        spec:
          restartPolicy: OnFailure

Remember

  • StatefulSet: stable identity and storage per Pod.
  • DaemonSet: one Pod per node.
  • Job: run to completion. CronJob: on a schedule.

Hands-on: solve four mysteries

Run each, diagnose it yourself, then check the solution.

  1. The phantom image: kubectl create deployment m1 --image=ngnix:1.27
    Solution

    Status ImagePullBackOff. describe shows “pull access denied… ngnix”. Typo: it’s nginx. Fix with kubectl set image deploy/m1 ngnix=nginx:1.27 (the container was named after the bad image).

  2. The greedy giant: kubectl create deployment m2 --image=nginx:1.27-alpine then kubectl set resources deploy m2 --requests=cpu=50,memory=1Ti
    Solution

    Status Pending. Events: “0/3 nodes are available: Insufficient cpu, Insufficient memory.” Requests must fit on a node. Set realistic values like cpu=100m,memory=64Mi.

  3. The fainting app: kubectl create deployment m3 --image=busybox:1.36 -- sh -c "echo starting; exit 1"
    Solution

    CrashLoopBackOff with growing restart delays. kubectl logs deploy/m3 --previous shows “starting”, and describe shows exit code 1. The program exits with an error; fix the command or app.

  4. The silent Service: 
    $ kubectl create deployment m4 --image=nginx:1.27-alpine
$ kubectl create service clusterip m4 --tcp=80:8080
$ kubectl run t --rm -it --image=busybox:1.36 --restart=Never -- wget -qO- -T 3 m4
    Solution

    Timeout. The EndpointSlice has the Pod, but on port 8080, and nginx listens on 80. The Service’s targetPort must be the container port: kubectl patch svc m4 -p '{"spec":{"ports":[{"port":80,"targetPort":80}]}}'.

Clean up: kubectl delete deploy m1 m2 m3 m4 and kubectl delete svc m4.

Remember

  • Read STATUS, then describe (Events), then logs --previous.
  • Service trouble: check EndpointSlices, selectors, and targetPort.
  • kubectl debug for images without shells.

Scheduling: affinity, taints & spreading

About 30 minutes.

You can control which nodes Pods land on, and keep copies spread out so one failure can’t take everything down.

Explain like I’m 5

Seating kids at a party:

nodeSelector / node affinity: “Kids who need a high chair sit at the table with high chairs.” Taints and tolerations: a table has a sign “Grown-ups only”. Kids can’t sit there unless they have a special pass (a toleration). Pod anti-affinity / topology spread: “Don’t put all the twins at the same table. If that table tips over, we lose all the twins!”

The engineer’s view
ToolSet onEffect
nodeSelectorPodSimple “only nodes with this label”
nodeAffinityPodRequired or preferred rules with operators (In, NotIn, Exists…)
podAffinity / podAntiAffinityPodNear or away from other Pods (e.g. cache next to app, replicas apart)
topologySpreadConstraintsPodEven spread across zones/nodes with a max skew

spec:
  template:
    spec:
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname   # or topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector: { matchLabels: { app: web } }
      tolerations:
        - key: gpu
          operator: Equal
          value: "true"
          effect: NoSchedule
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - { key: disktype, operator: In, values: [ssd] }
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  minAvailable: 2
  selector: { matchLabels: { app: web } }

To place a Pod only on special nodes, combine a taint (keeps others off) with node affinity (pulls yours on). A toleration alone just allows it.

Hands-on: party seating
  1. Label a node and pin a Pod to it: 
    $ kubectl label node fleet-worker2 disktype=ssd
$ kubectl run fast --image=nginx:1.27-alpine --overrides='{"spec":{"nodeSelector":{"disktype":"ssd"}}}'
$ kubectl get pod fast -o wide      # on fleet-worker2
  2. Taint a node and see Pods avoid it: 
    $ kubectl taint node fleet-worker gpu=true:NoSchedule
$ kubectl create deployment spread --image=nginx:1.27-alpine --replicas=4
$ kubectl get pods -l app=spread -o wide    # all on fleet-worker2
  3. Remove the taint and drain a node like you would for maintenance: 
    $ kubectl taint node fleet-worker gpu=true:NoSchedule-
$ kubectl rollout restart deploy spread        # rebalance
$ kubectl cordon fleet-worker2                 # no new Pods
$ kubectl drain fleet-worker2 --ignore-daemonsets --delete-emptydir-data
$ kubectl get pods -o wide                     # moved to fleet-worker
$ kubectl uncordon fleet-worker2

  • Affinity attracts, taints repel, tolerations permit.
  • Spread replicas across nodes and zones for resilience.

Autoscaling

About 30 minutes.

Your app grows when busy and shrinks when quiet, by itself.

Explain like I’m 5

An ice-cream shop on a hot day: a long queue forms, so the manager calls in more servers (more Pods: Horizontal autoscaling). If one server is struggling, give them a bigger scoop (more CPU/memory per Pod: Vertical autoscaling). If the shop is completely full of servers, open the room next door (more nodes: Cluster autoscaling). When evening comes, everyone goes home again.

The engineer’s view
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: php
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: php
  minReplicas: 1
  maxReplicas: 8
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 50 }   # % of the CPU request
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 120    # avoid flapping
  • The HPA needs metrics-server and CPU requests on the Pods: utilisation is measured against the request.
  • Custom and external metrics (queue length, requests per second) work via Prometheus Adapter or KEDA, which can also scale to zero.
  • VPA recommends or sets requests; don’t let VPA and HPA both act on CPU for the same workload.
  • Cluster Autoscaler and Karpenter add or remove nodes in the cloud based on Pending Pods and idle nodes.
Hands-on: summer rush
  1. Install metrics-server (kind needs the insecure-TLS flag): 
    $ kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
$ kubectl patch deployment metrics-server -n kube-system --type=json -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
$ kubectl top nodes        # wait a minute until numbers appear
  2. Deploy a CPU-hungry demo app with a CPU request: 
    $ kubectl create deployment php --image=registry.k8s.io/hpa-example
$ kubectl set resources deployment php --requests=cpu=200m
$ kubectl expose deployment php --port=80
$ kubectl apply -f hpa.yaml
  3. Open the floodgates in another terminal: 
    $ kubectl run load --rm -it --image=busybox:1.36 --restart=Never -- sh -c "while true; do wget -q -O- http://php; done"
  4. Watch the shop hire more staff: 
    $ kubectl get hpa php -w
NAME   TARGETS         MINPODS   MAXPODS   REPLICAS
php    cpu: 250%/50%   1         8         1
php    cpu: 120%/50%   1         8         5
  5. Stop the load with Ctrl+C and watch replicas drift back down after the stabilisation window. Clean up: kubectl delete hpa php, kubectl delete deploy,svc php.

Remember

  • HPA = more Pods; VPA = bigger Pods; Cluster Autoscaler = more nodes.
  • HPA on CPU needs metrics-server and CPU requests.
  • KEDA scales on events and can scale to zero.

kind: NetworkPolicy

spec:
  podSelector: {}               # every Pod in the namespace
  policyTypes: [Ingress]

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: api-from-web, namespace: shop }

Hands-on: badges and hallways
  1. Create the namespace and RBAC, then test as the ServiceAccount: 
    $ kubectl create namespace shop
$ kubectl apply -f rbac.yaml
$ kubectl auth can-i list pods -n shop --as=system:serviceaccount:shop:reader
yes
$ kubectl auth can-i delete pods -n shop --as=system:serviceaccount:shop:reader
no
$ kubectl auth can-i list secrets -n shop --as=system:serviceaccount:shop:reader
no
  2. Enforce the restricted Pod Security Standard and try a root Pod: 
    $ kubectl label namespace shop pod-security.kubernetes.io/enforce=restricted
$ kubectl run bad -n shop --image=nginx:1.27-alpine
Error from server (Forbidden): violates PodSecurity "restricted:latest": allowPrivilegeEscalation != false …
  3. Network rules: remove the PSA label for this step (kubectl label ns shop pod-security.kubernetes.io/enforce-), then: 
    $ kubectl run api -n shop --image=nginx:1.27-alpine -l app=api --expose --port=80
$ kubectl run web -n shop --image=busybox:1.36 -l app=web -- sleep 3600
$ kubectl run other -n shop --image=busybox:1.36 -l app=other -- sleep 3600
$ kubectl apply -f netpol.yaml
$ kubectl exec -n shop web -- wget -qO- -T 3 api | head -n 1     # allowed
$ kubectl exec -n shop other -- wget -qO- -T 3 api               # times out

Remember

  • RBAC: subject + binding + role. Grant the minimum.
  • Non-root, read-only filesystem, drop capabilities; enforce with Pod Security Admission.
  • Default-deny NetworkPolicies, then allow specific paths.

Helm & Kustomize

About 30 minutes.

Package and reuse your YAML across environments without copy-paste.

Explain like I’m 5

You have to make birthday invitations for ten friends. Writing each one from scratch is silly.

Helm is a fill-in-the-blanks card: “Dear ____, come to my party at ____.” You fill in the blanks (values) and print. You can even download ready-made card packs from a shop (chart repositories).

Kustomize is a stack of stickers: one plain card, plus a “for grandma” sticker that changes the time, plus a “for cousins” sticker that adds a map. No blanks, just layers on top.

The engineer’s view

Helm

$ helm repo add bitnami https://charts.bitnami.com/bitnami
$ helm search repo redis
$ helm install cache bitnami/redis --set architecture=standalone -n data --create-namespace
$ helm list -A
$ helm upgrade cache bitnami/redis -f my-values.yaml -n data
$ helm rollback cache 1 -n data
$ helm uninstall cache -n data

A chart is a folder: Chart.yaml (name, version), values.yaml (defaults), templates/ (Go-templated YAML). helm create mychart scaffolds one, helm template renders it locally, and helm lint checks it.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-web
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: web
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"

Kustomize (built into kubectl)

resources:
  - ../../base
namespace: prod
namePrefix: prod-
images:
  - name: ghcr.io/you/api
    newTag: "1.4.0"
patches:
  - target: { kind: Deployment, name: api }
    patch: |
      - op: replace
        path: /spec/replicas
        value: 5
configMapGenerator:
  - name: api-config
    literals: [LOG_LEVEL=warn]
$ kubectl kustomize overlays/prod       # preview
$ kubectl apply -k overlays/prod        # apply
Hands-on: cards and stickers
  1. Install Helm (brew install helm, winget install Helm.Helm, or the script on helm.sh).
  2. Scaffold, render and install your own chart: 
    $ helm create hello
$ helm template demo ./hello | head -n 40
$ helm install demo ./hello --set replicaCount=2
$ kubectl get pods -l app.kubernetes.io/instance=demo
$ helm upgrade demo ./hello --set replicaCount=3
$ helm history demo
$ helm rollback demo 1
$ helm uninstall demo
  3. Kustomize: make base/ containing your lesson-6 deploy.yaml and a kustomization.yaml with resources: [deploy.yaml]. Make overlays/dev/kustomization.yaml setting namePrefix: dev- and replicas 1. Run kubectl kustomize overlays/dev and compare.
Show the dev overlay

  - ../../base
namePrefix: dev-

  - pairs: { env: dev }

  - name: web
    count: 1

Remember

  • Helm: templated, versioned packages with install/upgrade/rollback.
  • Kustomize: base + overlays, no templating, built into kubectl.
  • Always render and review before applying.

Observability: logs, metrics & traces

About 30 minutes.

You can see what your cluster and apps are doing, and get told when something goes wrong.

Explain like I’m 5

A doctor checking on you uses three tools. The diary where you wrote what happened today (logs). The thermometer and heart-rate monitor showing numbers over time (metrics). And following you around the hospital to see which rooms you visited and how long you waited in each (traces). An alarm beeps when your temperature is too high (alerts).

The engineer’s view
  • Logs: write to stdout/stderr, ideally as structured JSON. The kubelet stores them per container; a DaemonSet agent (Fluent Bit, Vector, Promtail/Alloy) ships them to Loki, Elasticsearch or a cloud service before Pods disappear.
  • Metrics: Prometheus scrapes /metrics endpoints. kube-state-metrics exposes object state (desired vs available replicas); node-exporter exposes machine stats. The kube-prometheus-stack Helm chart installs all of it plus Grafana and Alertmanager.
  • Traces: instrument apps with OpenTelemetry to follow one request across services.
  • Watch the four golden signals: latency, traffic, errors, saturation. Alert on symptoms users feel, not on every blip.
groups:
  - name: app
    rules:
      - alert: PodCrashLooping
        expr: increase(kube_pod_container_status_restarts_total[10m]) > 3
        for: 5m
        labels: { severity: warning }
        annotations:
          summary: "{{ $labels.namespace }}/{{ $labels.pod }} restarting often"
Hands-on: the doctor’s kit
  1. Install the monitoring stack with Helm (it’s big; give it a few minutes): 
    $ helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
$ helm install mon prometheus-community/kube-prometheus-stack -n monitoring --create-namespace
$ kubectl get pods -n monitoring -w
  2. Open Grafana: 
    $ kubectl get secret -n monitoring mon-grafana -o jsonpath='{.data.admin-password}' | base64 -d; echo
$ kubectl port-forward -n monitoring svc/mon-grafana 3000:80
    Log in at http://localhost:3000 as admin. Browse Dashboards → “Kubernetes / Compute Resources / Namespace (Pods)”.
  3. Query Prometheus directly: 
    $ kubectl port-forward -n monitoring svc/mon-kube-prometheus-stack-prometheus 9090
    Try sum(rate(container_cpu_usage_seconds_total{namespace="default"}[5m])) by (pod). (Service names can vary slightly by chart version; check kubectl get svc -n monitoring.)
  4. Create a crash-looping Pod (kubectl create deployment boom --image=busybox:1.36 -- sh -c "exit 1") and find its restarts on a dashboard. Delete it afterwards.
  5. When done: helm uninstall mon -n monitoring to free your laptop’s memory.

Remember

  • Logs tell what happened, metrics show trends, traces show the path.
  • Log to stdout; ship logs off the node.
  • kube-prometheus-stack gives you Prometheus, Grafana and alerts in one install.

GitOps, operators & CRDs

About 35 minutes.

Git becomes the single source of truth for your cluster, and you understand how Kubernetes is extended.

Explain like I’m 5

GitOps: the class has one official rulebook on the teacher’s desk (a git repository). A helper robot constantly compares the classroom with the rulebook. If someone moves a desk without changing the rulebook, the robot moves it back. Want a change? Write it in the rulebook first, and the robot does the rest.

CRDs and operators: Kubernetes knows words like Pod and Service. A CRD teaches it a new word, like “Database”. An operator is an expert robot that knows what to do with that word: create the database, back it up every night, repair it if it breaks.

The engineer’s view

GitOps

  • All manifests (plain, Kustomize or Helm values) live in git. Changes happen through reviewed pull requests, giving you an audit log and easy rollback with git revert.
  • Argo CD and Flux run inside the cluster, watch the repo, and sync. They report drift and can self-heal it.
  • Common split: an app repo (code + Dockerfile; CI builds images) and a config repo (manifests; CI or a bot bumps the image tag).
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: guestbook
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/argoproj/argocd-example-apps
    path: guestbook
    targetRevision: HEAD
  destination:
    server: https://kubernetes.default.svc
    namespace: guestbook
  syncPolicy:
    automated: { prune: true, selfHeal: true }
    syncOptions: [CreateNamespace=true]

CRDs and operators

apiVersion: postgresql.cnpg.io/v1
kind: Cluster                  # a new kind, added by a CRD
metadata:
  name: notes-db
spec:
  instances: 3                 # the operator creates 3 Postgres Pods,
  storage: { size: 1Gi }       # replication, failover and backups

An operator is a custom controller running the same reconciliation loop as Kubernetes’ built-in controllers, but encoding expert knowledge for one system. Popular ones: CloudNativePG, Strimzi (Kafka), cert-manager, Prometheus Operator. Frameworks like Kubebuilder and Operator SDK help you write your own.

Hands-on: the rulebook robot
  1. Install Argo CD: 
    $ kubectl create namespace argocd
$ kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
$ kubectl wait -n argocd --for=condition=available deploy --all --timeout=300s
  2. Open the UI and log in as admin: 
    $ kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 -d; echo
$ kubectl port-forward -n argocd svc/argocd-server 8443:443
    Visit https://localhost:8443 and accept the self-signed certificate warning.
  3. Create the Application and watch it sync: 
    $ kubectl apply -f argocd-app.yaml
$ kubectl get pods -n guestbook
  4. Cause drift and watch self-healing: 
    $ kubectl scale deploy guestbook-ui -n guestbook --replicas=5
$ kubectl get deploy -n guestbook -w      # snaps back to git’s value
  5. See CRDs in your cluster: kubectl get crd. Argo CD added several, including applications.argoproj.io. Try kubectl explain application.spec.
  6. Clean up: kubectl delete -f argocd-app.yaml then kubectl delete namespace argocd guestbook.
Fork the example repo, point repoURL at your fork, change the replica count in git, push, and watch Argo CD apply it with no kubectl at all.

Remember

  • GitOps: git is the source of truth; an in-cluster agent syncs and heals drift.
  • CRDs add new object types; operators run the expert logic behind them.
  • Everything in Kubernetes is the same idea: declare, then reconcile.

Capstone: run a production-style app

3–6 hours. Uses everything.

A notes app with web front end, API, Redis cache and PostgreSQL, deployed to your cluster the way real teams do it.

Requirements checklist
  1. Images: build web and api images (any language). The API offers GET/POST /api/notes stored in Postgres, a visit counter in Redis, /healthz and /ready, and returns its Pod name. Load into kind with kind load docker-image IMAGE --name fleet, or push to a registry.
  2. Namespace notes with Pod Security restricted, a ResourceQuota and a LimitRange.
  3. Config: ConfigMap for settings; Secret for the database password (never committed in plain text).
  4. Database: Postgres StatefulSet with a headless Service and volumeClaimTemplates (or the CloudNativePG operator for bonus points).
  5. API: Deployment with startup/readiness/liveness probes, requests and limits, non-root securityContext, a PodDisruptionBudget, topology spread, and an HPA (2–6 replicas at 60% CPU).
  6. Web: Deployment + Service; Ingress routing / and /api.
  7. NetworkPolicies: default deny; allow ingress-controller → web/api, api → postgres and redis, plus DNS egress if you deny egress.
  8. Packaging: everything in a Helm chart or Kustomize base with dev and prod overlays.
  9. Delivery: manifests in git, synced by Argo CD. CI builds images and bumps the tag.
  10. Observability: a Grafana dashboard for API latency and error rate, and an alert for crash loops.
  11. Prove it: kill API Pods during a load test and see no errors; delete the Postgres Pod and confirm notes survive; roll out a broken image and roll back.
